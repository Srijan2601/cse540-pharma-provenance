# Design decisions and open questions

The proposal (10/25) fixes the architecture but leaves some details open. This register lists each gap, the answer the **11/01 draft** proposed, and what the code does. Every **Status** was checked against the code on 2026-11-25.

The draft marked C2, C5, C6 and D3 "needs vote". The team voted on all four and adopted the draft's recommended answer for each. The code implements C2, C5 and C6 as drafted, and D3 is a schedule question, not code.

IDs are referenced from code comments (`Design decision C3`) and from [`contracts/README.md`](../contracts/README.md).

**Status values:** `Accepted by team vote` marks the four items the draft put to a vote. `Implemented as drafted` means the code does what the draft answer says. `Implemented, with this change` names where the code differs from it. `Process note` marks an item about how the team works, which the code cannot show.

## Contract (C)

| ID | Question | Draft answer | Status |
|---|---|---|---|
| **C1** | Which function causes each status transition, and which event does it emit? Table I has no function that moves a lot from Created to InTransit. | `initiateTransfer`: Created/Stored → InTransit. `acceptTransfer`: → Stored. `updateStatus`: InTransit ⇄ Stored. `markDelivered`: Stored → Delivered, emitting `StatusUpdated`. Each write emits exactly one event (table in `contracts/README.md`). | Implemented as drafted. Added since the draft: `updateStatus` rejects every other pair of statuses with `InvalidStatusTransition`. |
| **C2** | What does "active" mean, which states are terminal, and can a Delivered or Compromised lot be recalled? The proposal conflicts with itself: Fig. 1 says "active -> Compromised \| Recalled" (recall from active lots only), but data flow 4 says the regulator can "recall a lot at any stage". | Active = Created, InTransit, Stored. Delivered, Compromised and Recalled are terminal for custody. `recallBatch` works from any status except Recalled. `issueCertificate` works in any status except Recalled. Entering Compromised or Recalled clears an open hand-off. (Stretch: a regulator `clearExcursion`.) | Accepted by team vote. Implemented as drafted. The stretch `clearExcursion` was not built: no function undoes Compromised. Added since the draft: `recallBatch` rejects an empty reason with `EmptyReason`. |
| **C3** | Initiate/accept hand-off rules: who can initiate, to whom, and how a hand-off to a wrong address is undone. | Only the custodian initiates, and only one hand-off per lot can be open. Routes: MANUFACTURER → DISTRIBUTOR; DISTRIBUTOR → DISTRIBUTOR or RETAILER. Custody changes on **accept**. Added `cancelTransfer` and the `TransferCancelled` event, which restore the previous status. The draft left open whether MANUFACTURER → RETAILER should be allowed directly. | Implemented as drafted, with one clarification: routes are checked by role. A hand-off to a pharmacy needs the sender to hold `DISTRIBUTOR_ROLE`, so a manufacturer cannot ship straight to a pharmacy unless the regulator has also made it a distributor. |
| **C4** | Roles gate functions, not lots. How is "REGULATOR (admin)" mapped onto OpenZeppelin? | Every custody action requires the role **and** being the custodian (or pending custodian). The constructor gives the regulator `DEFAULT_ADMIN_ROLE` and `REGULATOR_ROLE`, and the regulator is the admin of the four organization roles. A revoked organization's lots stay where they are and can still be recalled. | Implemented as drafted. |
| **C5** | Batch field types, the ID scheme, duplicate lots, and what "product hash" is a hash of. | IDs are a counter starting at 1. `productHash = keccak256(abi.encode(productCode, lotNumber))`, unique. Origin = the manufacturer's address. `manufactureDate` is passed in and `registeredAt` = block time. Documents are `DocumentRef {cid, contentHash}`. **Risk:** uniqueness is global, so any MANUFACTURER can register, or front-run, another firm's product code + lot number, and `recallBatch` does not free the hash. Options: (a) scope per manufacturer with key = `keccak256(abi.encode(msg.sender, productHash))` and `batchIdOf(address manufacturer, bytes32 productHash)`; (b) the regulator binds product codes to manufacturers. | Accepted by team vote. Implemented as drafted: the product hash is unique across all manufacturers. Neither option (a) nor (b) was built, so the risk stands; `contracts/README.md` lists it under "Trust assumptions". Added since the draft: `registerBatch` rejects a zero product hash (`ZeroProductHash`) and a manufacture date that is 0 or in the future (`InvalidTimestamp`). |
| **C6** | Who certifies? Step 1 has the manufacturer upload "its certificate", but `issueCertificate` is the regulator's. | The manufacturer's certificate of analysis is referenced **inside the metadata JSON**. `certificate` is set only by the regulator through `issueCertificate` and is overwritten each time, with history kept in `CertificateIssued` events. No shipping gate in the MVP. The verify page shows "uncertified" if it is empty. | Accepted by team vote. Implemented as drafted. The certificate of analysis is an attachment of the lot metadata. For a lot without a certificate the verify page notes that no regulator certificate has been issued. |
| **C7** | What does the on-chain temperature range do? Units, the excursion rule, and the oracle function signatures. | `int16` in tenths of a °C, set at registration and fixed (2–8 °C = 20..80). `reportExcursion` checks on-chain that the reading is outside the range, then sets Compromised. `anchorSensorLog` stores only the latest log plus a count. The off-chain rule (e.g. K consecutive out-of-range samples) lives in `oracle/`. | Implemented as drafted. The range check is on-chain (a reading equal to a bound is in range). The rule is off-chain in `oracle/`: K consecutive out-of-range readings, K = 3 by default (`EXCURSION_RUN_LENGTH`). Added since the draft: `reportExcursion` rejects an `observedAt` that is 0 or in the future (`InvalidTimestamp`). |

## Off-chain and integration (O)

| ID | Question | Proposed answer | Status |
|---|---|---|---|
| **O1** | How does the verify page "check IPFS files against their on-chain hashes"? A UnixFS CID is **not** a plain hash of the file's bytes. | Store the CID (to find the file) **plus** `keccak256(exact uploaded bytes)` (to verify it). The page fetches the file, runs `ethers.keccak256(bytes)` and compares. This is built into `DocumentRef`. Never re-serialize JSON after hashing. | Implemented as drafted. The verify page fetches each file by its CID and compares `keccak256` of the bytes with the recorded hash. `npm run ipfs:verify` in `oracle/` does the same on the command line and also checks the digest inside the CID. |
| **O2** | No schemas for the three IPFS documents (lot metadata, certificate, sensor log). | Add `docs/schemas/*.schema.json`, each with a `schemaVersion`, plus synthetic examples. Use integer tenths of °C and Unix seconds, and include `chainId`, registry address and `lotId` in each document so it can't be reused for another lot. | Implemented, with this change: lot metadata is written before the lot has an ID, so it names the lot by `productCode` and `lotNumber` instead of `lotId`. See [`schemas/`](schemas/). |
| **O3** | A pinning-service API key in the React app would ship in the **public** JS bundle. | Pick one: (a) a small upload service that holds the key and returns `{cid, contentHash}`; (b) scoped or short-lived upload tokens; (c) demo-only CLI upload with a pasted CID. Choose one provider and one gateway. | Implemented: option (a). The upload service in `oracle/` (`npm run service`) holds any storage credential; the browser never does. By default it needs none, because files go to a local content-addressed store. Kubo and Pinata are optional back ends, and Pinata has not been run against the live service. |
| **O4** | How do the frontend and oracle get the ABI and address? Plus the local-network fallback. | `scripts/deploy.js` writes `deployments/<network>.json` (address, chainId, deployBlock, txHash, ABI). The draft also planned a seed-demo script, a local IPFS fallback with the same CIDs, and a first Amoy deployment. | Implemented. The Amoy deployment was made on 2026-11-26, and its record is committed as `deployments/amoy.json`. Deployment records are written as drafted, and the ABI alone is committed as `deployments/abi/ProvenanceRegistry.json`; a test fails when it is stale. `scripts/demo.js` takes two lots through the journey, one to delivery and one to an excursion and a recall. The local file store in `oracle/` gives a file up to 256 KiB the same CID that IPFS gives it (see `oracle/README.md`). |
| **O5** | "Encrypting confidential documents" conflicts with public verification, and public IPFS is not private. | Classify the data. Public plaintext: lot metadata, regulator certificate, sensor logs. Encrypted with AES-256-GCM (keys shared out of band): e.g. invoices and pricing, where the hash covers the ciphertext. Never uploaded: personal data. All fixtures in this repo are synthetic. | Implemented as drafted. Confidential attachments are encrypted before upload, in the dashboard (the "Confidential: encrypt before upload" option when registering a lot) or with `npm run ipfs:add -- <file> --encrypt` in `oracle/`. Either way the key is shown once, and the recorded CID and hash cover the encrypted bytes. |
| **O6** | What does `verifyBatch` return, what does the QR code encode, and where does history come from? | `verifyBatch` is a public view returning the `Batch` struct. History comes from events (paged `getLogs` from `deployBlock`). QR = `https://<host>/verify?chain=80002&registry=0x…&lot=<id>`. Host the page publicly, never on localhost, and read it with a keyless RPC. | Implemented, with these changes: the QR code encodes `<app URL>#/verify?lot=<id>&chain=<chainId>&registry=<address>` (the route sits in the URL hash, so any static host can serve it), and the verify page refuses a link whose registry is not a deployment the app knows. Public hosting of the verify page was not set up. |

## Delivery and process (D)

| ID | Question | Proposed answer | Status |
|---|---|---|---|
| **D1** | Definition of done for each deliverable, and a reproducible graded state. | 11/01: `npm ci && npm run compile && npm test` passes on a fresh clone, and the interface declares every Table I function and Fig. 1 event. Tag releases `v0.1-contract-draft`, `v0.2-midterm`, `v1.0-final`. | Process note. On 2026-11-25 `npm ci`, `npx hardhat compile` and `npx hardhat test` passed on a clean copy of the working tree. The repository has no release tags. |
| **D2** | Nothing enforces "every PR reviewed" and "main always passes tests". | `.github/workflows/ci.yml` and a PR template. The draft also planned a branch ruleset on `main` (PRs only, 1 approval, required CI check, no force pushes) and a GitHub Projects board with Owner, Due and Milestone fields and a `stretch` label. | Process note. The workflow and the PR template exist; the workflow has three jobs (contracts, oracle, frontend). The ruleset and the board are GitHub settings, which the repository's files cannot show. |
| **D3** | The integration session and the Canvas submission (48 h early) fall on the same day. | Internal dates. Midterm: freeze 11/11, integrate 11/12, submit 11/13. Final: features complete 11/25, integrate 12/01, submit 12/02. Decide on ERC-721 lot tokens before the struct is final. | Accepted by team vote. Process note: the dates are the team's internal plan and nothing in the code depends on them. The code has no ERC-721 token; a lot is a `Batch` record in the registry. |
| **D4** | Where QA testing ends and unit testing begins. | Unit and revert tests go in `test/ProvenanceRegistry.test.js`. An end-to-end journey test (data flows 1–5) goes in `test/integration/`. The QA test plan (role × function matrix) and the manual dashboard/QR checklist go in `docs/testing/`. | Implemented, with this change: the unit tests are split by module under `test/unit/` (the single test file is gone), and `test/solidity/` (fuzz tests) and `test/tooling/` were added. The role × function matrix is an executable test. The test plan is [`testing/README.md`](testing/README.md). No manual checklist for the dashboard and the QR code was written. |
| **D5** | Analysis method and where the raw data lives. | Gas: `npm run test:gas -- --gas-stats-json docs/analysis/data/gas-<commit>.json`, cross-checked against Amoy receipts and priced at a dated POL price. The centralized-database and Fabric comparisons are qualitative criteria tables. | Implemented, with this change: the gas data comes from `npm run gas:report`, which writes `docs/analysis/data/gas-report.json` and `gas-report.md`; a test fails when they are stale. The committed report lists gas only, with no POL price. The Amoy deployment of 2026-11-26 provides receipts for the cross-check, which has not been done in this repository; its demo run reported about 20% more gas than the same run on a local node, so the cross-check matters. The comparison tables belong to the report, which is not in this repository. |
| **D6** | Where the project log lives. The repo is public. | Attendance, missed commitments and conflicts go in a **private** shared doc. The repo holds only decisions and action items (`docs/meetings/`). Never commit the proposal or team-contract PDF (it contains student IDs). | Process note. `docs/meetings/` holds only the template, and `.gitignore` blocks files named like the proposal or the team-contract PDF. |
